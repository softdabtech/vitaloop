# Cline: локальный аудит и исправления VITALOOP

Исходный документ: `/Users/oleksii/Documents/VITALOOP/projects/VITALOOP_service_structure_2026-10-01 (2).docx`.
Рабочий проект: `/Users/oleksii/Documents/VITALOOP/projects/vitaloop`.
Это английская версия VITALOOP. Украинская версия находится отдельно в `../vitaloop_ua`; кабинет и часть логики общие, поэтому сверяй UA только для понимания локализации и общих компонентов. Не меняй `vitaloop_ua`, если исправление явно не требует отдельного изменения там.

## Порядок работы

1. Отдельно выполни полный read-only аудит локального проекта и сопоставь его с DOCX.
2. Выдай отчёт, список подтверждённых дефектов и порядок исправлений. На этом этапе исходники не меняй.
3. После моего выбора ID исправлений переходи к локальным изменениям небольшими проверяемыми порциями.

## Промт 1: аудит без изменений кода

```text
Работай только с локальным репозиторием `/Users/oleksii/Documents/VITALOOP/projects/vitaloop` и документом `../VITALOOP_service_structure_2026-10-01 (2).docx`.

Цель: провести доказательный аудит реализации VITALOOP EN по всем пользовательским и операционным сервисам, описанным в DOCX. Документ является оценкой продукта, а не спецификацией, автоматически разрешающей реализовать все перечисленные идеи. Самостоятельно проверь каждое применимое утверждение по текущему коду, тестам и конфигурации.

ОГРАНИЧЕНИЯ
- Это строго локальная работа. Не подключайся по SSH, не деплой, не пушь, не выполняй запросы, изменяющие production/staging или удалённую БД.
- Не открывай и не выводи содержимое `.env`, ключей, токенов, сертификатов и пользовательских данных. Проверяй только наличие/валидность переменных, если это нужно для аудита.
- Сначала выполни `git status --short` и зафиксируй уже существующие изменения. Они принадлежат пользователю: не перезаписывай, не форматируй, не удаляй, не stash/reset/checkout и не включай их в свои выводы как новые изменения.
- Ничего не редактируй и не устанавливай на этапе аудита. Не запускай команды, которые меняют данные. Тесты и health checks допустимы только локально и read-only.
- Не считай наличие экрана, endpoint или теста доказательством полноценной пользовательской функции. Не считай непроверенную внешнюю интеграцию работающей.
- Не придумывай клинические правила, red-flag thresholds, референсные диапазоны, диагнозы или медицинские рекомендации. Если требование нуждается в клиническом/юридическом утверждении, обозначь его как блокер.

ПЕРЕД НАЧАЛОМ
1. Прочитай локальные инструкции проекта (если есть), README и RUNBOOK; RUNBOOK используй только для понимания архитектуры, не для операций на сервере.
2. Проверь текущую ветку и `git status --short`; изучи уже имеющийся diff только для контекста, не меняй его.
3. Составь карту frontend, backend, CRM, интеграций, миграций, тестов и основных пользовательских маршрутов. Исключи из полного обхода generated output, `node_modules`, `.venv`, build artifacts, uploads и секреты.
4. Проследи реальные data flows: UI -> API -> auth/authorization -> persistence -> обработка/ответ -> UI. Для критичных потоков найди фактические тесты и их ограничения.

ОБЛАСТЬ АУДИТА ИЗ DOCX
- Вход, регистрация, восстановление доступа, onboarding и правила редактирования профиля здоровья.
- Symptom check: контролируемость входных данных, adaptive flow, feature flags/rollout, внешняя медицинская интеграция, red flags и поведение при срочном ответе.
- Передача symptom context в лабораторный отчёт и возможность/триггер пересчёта после изменения симптомов или профиля.
- Загрузка PDF/изображений, OCR, подтверждение сомнительных значений, нормализация названий и единиц, лабораторные reference ranges и поведение при отсутствующем диапазоне.
- Паттерны, гипотезы, ограничения уверенности, персональный итоговый разбор и объяснимость рекомендаций; fallback/AI ошибки и разделение клинического контента и коммерческих ссылок.
- Dashboard, полный отчёт, сетевые/error/empty states, Lab Plan, baseline/история/динамика, weekly check-in и Insights.
- EN кабинет; локализацию и общий кабинет сравнивай с UA только для выявления EN-дефектов или общих дефектов. Не расширяй область до отдельного UA-рефакторинга.
- Подписка/биллинг, поддержка, уведомления, CRM workflow и B2B интеграции: проверь код и тесты, отдельно обозначь то, что нельзя подтвердить без реальной внешней среды.
- Экспорт, удаление и хранение пользовательских данных; authz/изоляция пользователей; мониторинг и эксплуатационные проверки.

ПРИОРИТИЗАЦИЯ ДОКУМЕНТА
- P0: безопасность symptom check.
- P1: персональный итоговый разбор; связь симптомов с отчётом; надёжность оценки биомаркеров.
- P2: обоснованность рекомендаций; упрощение кабинета; цикл check-in -> повторная оценка.
- P3: коммерческая и языковая готовность.
Используй приоритеты как порядок проверки, но независимо оцени техническую severity, вероятность, влияние и доказанность. P0 не даёт разрешения самостоятельно изобретать клиническую матрицу: без утверждённых медицинских правил фиксируй обнаруженный технический дефект и безопасные варианты, а клиническое поведение оставляй заблокированным.

КАК ФОРМИРОВАТЬ РЕЗУЛЬТАТ
Для каждого утверждения/проблемы из DOCX укажи:
1. ID и название; соответствующий раздел/приоритет DOCX.
2. Статус: подтверждённый баг / возможный баг / продуктовый gap (требует новой функциональности) / внешняя или клиническая зависимость / не подтверждено кодом.
3. Доказательства: точные файлы, символы и строки; фактический путь данных; относящиеся тесты и что именно они доказывают.
4. Влияние, severity, confidence; минимальный способ воспроизвести локально, если возможно.
5. Рекомендуемый следующий шаг и безопасный критерий готовности.

Не утверждай, что проверил то, что нельзя доказать локально: live платежи, production delivery уведомлений, доступность внешнего провайдера, клиническую полезность, юридическое соответствие и production rollout. Отдельно укажи тестовые команды и результаты, какие проверки не удалось выполнить и почему. Не запускай автоматически полный медленный/внешний набор, если он меняет данные; сначала объясни риск.

В конце выдай:
- краткий вывод о наиболее значимых доказанных дефектах;
- таблицу приоритетов P0-P3 с ID, зависимостями и блокерами;
- предложенные маленькие implementation slices (по одному связанному поведению на slice);
- перечень вопросов, требующих решения владельца продукта/клинициста;
- подтверждение, что исходники не менялись.

На этом остановись. Не начинай исправления до моего отдельного подтверждения выбранных ID.
```

## Промт 2: локальные исправления после аудита

Перед запуском замени `<ID>` на подтверждённые ID из отчёта и приложи сам отчёт Cline.

```text
Исправь локально только подтверждённые пункты аудита: <ID>.
Рабочий репозиторий: `/Users/oleksii/Documents/VITALOOP/projects/vitaloop`.
Используй приложенный аудит как основание; если код противоречит выводу отчёта, сначала перепроверь источник истины и объясни расхождение.

Ограничения:
- Только локальный код и локальные тесты. Не SSH, не deploy, не push, не production/staging API или БД.
- Перед правкой заново проверь `git status --short`; сохрани все пользовательские изменения. Не трогай файлы с существующими правками, пока не прочитал и не понял их контекст.
- Не читай и не печатай секреты. Не используй и не вставляй тестовые логины/пароли в исходники, команды, тесты или отчёты.
- Не добавляй миграции, новые продуктовые функции, клинические пороги или medical copy, если это не входит в выбранный ID и не имеет утверждённого источника.
- Один небольшой slice за раз. Сначала назови конкретную гипотезу о причине и самый дешёвый тест, который её опровергнет; затем сделай минимальный root-cause fix и сразу запусти этот тест. При падении исправляй тот же slice и повторяй тот же focused test.
- Используй имеющиеся архитектуру, helpers и test patterns. Не делай unrelated cleanup/refactor.
- Не считай существующий тест достаточным, если он не покрывает изменённый сценарий; добавь/обнови узкий regression test.

Для каждого выбранного ID:
1. Найди владельца поведения и конкретный воспроизводимый путь.
2. Подтверди дефект тестом/диагностикой до изменения, если это возможно.
3. Исправь только согласованное поведение и добавь регрессионное покрытие.
4. Запусти focused test, затем необходимые проверки затронутого слоя.
5. Сообщи изменённые файлы, причины, команды/результаты тестов, остаточные риски и что осталось заблокировано.

Для клинически чувствительных изменений (red flags, thresholds, диапазоны, медицинские рекомендации) остановись до изменения поведения, если в задаче нет утверждённой врачом спецификации. Можно исправлять техническое нарушение уже утверждённого правила, но не менять само правило.

После каждого slice остановись и покажи результат. Не переходи к следующему ID автоматически, если его реализация затрагивает другую подсистему, меняет контракт или требует нового продуктового решения.
```
